# APFD policy and replay evidence

The opt-in `faster.optimizeFor: 'apfd'` policy promotes cached failures, then
edited/new tests, transitively affected tests and remaining tests. Each bucket
honors manifest priorities, then ranks by `durationRank + 0.1 * sizeRank`
descending, using the global FAST order for ties. Both ranks use distinct values
within the project. The weight is fixed in production. Current fault identities
and current execution outcomes are never ranking inputs.

```bash
faster run --faster.optimizeFor=apfd --no-file-parallelism --maxWorkers=1
```

## Verify the recorded improvement

From the repository root, after installing workspace dependencies:

```bash
pnpm exec node --import tsx research/apfd/evaluate.ts
```

This command calls the production rank scorer, reconstructs the six APFD buckets
from recorded features, and asserts that all 93 complete permutations match the
frozen chosen orders. It then scores those orders, the previous implementation
and all 30 recorded repetitions of each randomized control. Fault labels live
under `evaluation`; the ranking function accepts only `features`. There are no
local absolute paths or downloads.

| Same 93 live Jsoup suites | Mean APFDf ↑ | New policy wins / losses / ties |
| --- | ---: | ---: |
| APFD policy | 0.9398 | — |
| Previous FASTER | 0.7375 | 81 / 0 / 12 |
| Ekstazi + random | 0.6536 | 92 / 1 / 0 |
| Fastazi-S | 0.5807 | 86 / 7 / 0 |
| Fastazi-P | 0.5616 | 87 / 6 / 0 |
| FAST-pw | 0.3990 | 87 / 6 / 0 |
| Random | 0.5383 | 92 / 1 / 0 |
| Vitest base | 0.7267 | 81 / 1 / 11 |

For one curated fault per version, `APFDf = 1 - (firstFaultRank - 0.5) / N`,
where `N` is the full live suite size. A control that misses the fault scores
zero. The first revealing class counts once even if several methods fail. Higher
APFDf is better; smaller first-fault rank is better. Comparisons against
randomized controls use each version's mean across repetitions. Ekstazi is a
selector; its control uses random ordering after selection.

The mean first revealing class moves from 7.35 to 1.96. At a budget of
`floor(0.5 * EkstaziSelectedCount)` per version, the new policy reveals 92/93
faults, compared with 64/93 previously and Ekstazi's mean detection probability
of 53.7%. At the full selected-count budget it reveals 93/93, compared with 91/93
previously. The evaluator prints all twelve paper budgets, from 10% to 100%.
Faster retains the complete suite: these are ordered-prefix results, not claims
of selection savings or reduced total execution cost.

## What this evidence establishes

This is an ordering replay of an already executed, inspected and **tuned cohort**.
The hillclimb retained 58 candidate configurations after exploratory probes. It
selected a simple high-scoring policy with no individual regressions against
previous FASTER on these versions. The 0.05 and 0.1 breadth weights tied on mean
APFDf and comparison counts; production uses 0.1. All 93 versions were available
for tuning, so none is an independent holdout for this policy.

Versions follow the recorded chronological Git sequence. Change features compare
current source/dependency hashes with the previous completed fixed run; they are
not randomly simulated edits. Each target reintroduces a curated fault while
exposing fixed/repair tests. In 90/93 versions an existing fault-revealing test
was edited, two more revealing classes were new and one case was the cold start.
This makes edited/new test promotion unusually informative. It can overstate the
benefit in natural CI despite being a legitimate pre-execution signal.

Without edited/new promotion, the history/breadth blend scored only 0.7434. An
experimental production-changes-only specificity policy scored 0.8060 with
57 improvements, 23 regressions and 13 ties against previous FASTER. That
ablation is a separate policy and is not shipped here. It does not show that the
implemented policy retains 0.9398 without repair-test signals.

The frozen policy was also executed through the built FASTER CLI on 17 previously
inspected UFO regressions, with preserved previous caches and repair tests. Its
APFDf improved from 0.9048 to 0.9455: two improvements, zero regressions and
15 ties. All 17 fixed controls passed and all target method identities and
pass/fail/skip outcomes matched previous runs. Those 34 executions are supporting
native evidence, not regenerated by this Java ordering replay. The earlier
untouched-history audit revealed no faults in those 17 targets.

These live-suite controls are related to Greca et al.'s 2022 file-based selection
and similarity-based prioritization study. They are **not the published scores**:
the published experiment covers 541 versions across 12 subjects and uses
different suite-cache membership and ordering seeds. This artifact supports
APFDf and budget comparisons on one matched subject. CPU, selection safety,
multi-subject replication and a publication-level generalization claim remain
separate work.

## Fixture format and provenance

`fixtures/jsoup-tuning.jsonl` contains one object per version. `features.files`
records class identifiers, current source byte counts, previous durations and
failure flags, and recorded source-history classifications. Durations of `null`
mean no previous observation. Orders and fault identities are integer indices
into that version's `features.files`; control orders may contain only selected
files. Fixed and buggy Git commits identify the targets.

`fixtures/provenance.json` records the fixture SHA256 and hashes of its preserved
source artifacts. The compact fixture contains 2,449 file observations and all
recorded control permutations, but excludes raw Java sources, execution logs and
dependency graphs. It cannot independently regenerate the recorded affectedness
or execute the Java targets. The original sealed artifacts remain in the research
workspace under `outputs/greca22-*`; their hashes allow reconciliation without
rewriting them. The evaluator checks fixture integrity before ranking. Real
Vitest integration tests separately exercise source tracking, bucket behavior,
cache lifecycle and configuration compatibility.

## Follow-up stack

1. **This PR: policy and evidence.** Freeze ranking semantics and document the
   limits above. Keep the default DX objective and an explicit APFD opt-in.
2. **Performance PR on this branch.** Profile source hashing, dependency traversal
   and FAST candidate selection. Require identical complete orders on the frozen
   fixture and integration scenarios; report cold/warm CPU, wall time, memory,
   file reads and overhead separately. A policy change belongs in another study.
3. **Replication PR on the performance branch.** Evaluate the frozen policy on
   fresh projects and chronological CI histories. Preserve predictions before
   reading outcomes, include unchanged existing tests and natural failures, and
   report results separately for test edits, new tests and production-only edits.
   Match the paper's RQ1 fault detection/APFDf, RQ2 budgets and RQ3 overhead where
   protocols permit, retaining every attempted version and reason for exclusion.

The publication question is whether the APFD gains survive that fresh evaluation
without the repair-test advantage. The current evidence justifies testing that
question; it does not answer it yet.
